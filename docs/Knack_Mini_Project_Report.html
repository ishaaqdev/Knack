Abstract

Technical competence alone no longer determines the employability of an engineering graduate. Recruiters consistently report that fresh graduates struggle to communicate under pressure, reason through ambiguous requirements, and use generative AI tools without accepting their output uncritically. These abilities are behavioural rather than declarative: they cannot be acquired from lecture videos or multiple-choice tests, which is precisely how most existing soft-skill training platforms deliver them.

This report presents Knack, a web application that reframes soft-skill practice as a short daily exercise. A trainee selects one of three tracks — Workplace Communication, Critical Thinking, or AI Fluency — and receives a realistic workplace scenario generated by a large language model. The trainee writes the response they would actually send, and the same model grades it on a ten-point rubric, returning what worked, what was missing, and one concrete improvement. Experience points, daily streaks, per-track skill scores and a composite Professional Readiness Score convert this into a repeatable habit.

The distinguishing contribution of the system is multi-source personalisation under a bounded token budget. Scenarios are conditioned on three independent signals: an eight-field stated profile captured at onboarding; an optional distillation of the trainee's public GitHub repositories, which supplies the technologies they genuinely work with; and a derived learner context that the model rewrites every three attempts from a six-attempt window. Because only the rewritten summary is ever injected — never the raw history — prompt size remains constant irrespective of how long a trainee has been training. Empirical testing showed the grader to be well separated (a considered response scored 9/10 against 1/10 for a deliberately evasive one), the derived context to correctly identify a planted recurring weakness and reference it in later feedback, and profile substitution to change scenario content substantially. A documented failure mode is also reported: injecting the free-text portfolio summary caused the model to anchor on a single project, which was resolved by restricting prompt input to bounded technology and domain lists.

The system is implemented as a React 19 single-page application with a Node.js and Express 5 backend, SQLite persistence, scrypt-based authentication, and Gemma 4 accessed through OpenRouter. A model fallback chain and a deterministic offline scenario bank keep the application usable when the free-tier inference endpoint is rate-limited.

Chapter 1
Introduction

1.1 Background and Motivation

Employability surveys of Indian engineering graduates have for over a decade reported the same finding: the binding constraint on placement outcomes is not technical knowledge but communication, reasoning and professional judgement. A graduate who can implement a balanced binary search tree may still be unable to tell a team lead that an estimate has slipped, to identify that a stated requirement does not match the real need, or to notice that a generated code snippet calls a library function which does not exist.

These are behavioural competencies. They are acquired the way any skill is acquired — by repeated attempts against realistic situations, followed by specific feedback. Yet the training available to students is overwhelmingly declarative: recorded lectures on “effective communication”, followed by multiple-choice assessments. A student can score full marks on such an assessment without ever having composed a difficult message.

Two developments make a different approach feasible. First, instruction-tuned large language models can now generate plausible, specific workplace situations and assess free-text responses against a stated rubric with reasonable consistency. Second, several providers expose capable models at zero marginal cost under rate limits, which removes the economic barrier that previously made per-student generative content impractical for a student project.

The remaining difficulty is that a generic AI tutor is only marginally better than a generic video. If every trainee receives the same scenario distribution, the system is a content library with extra latency. The value appears only when the generated situation resembles the one the trainee will actually walk into — which requires the system to know who the trainee is, what they build, and where they have previously failed.

1.2 Problem Statement

To design and implement a web-based soft-skill training system that (i) generates workplace scenarios personalised to an individual trainee's academic stage, technical background and demonstrated weaknesses; (ii) assesses free-text responses with a calibrated rubric and returns actionable feedback; (iii) maintains a constant inference cost per interaction irrespective of accumulated user history; and (iv) remains usable when the external inference service is unavailable.

Requirement (iii) deserves emphasis, because it is the constraint that shapes the architecture. The obvious way to personalise from history is to place previous attempts into the prompt. This is unsustainable: prompt length grows linearly with usage, cost grows with it, and on a small model the additional context measurably degrades output quality. A system that becomes slower, more expensive and worse the more a student uses it is not a training system.

1.3 Objectives

  1. Multi-source personalisation. Condition scenario generation on three independent signals — a stated profile collected at onboarding, an optional distillation of the trainee's public GitHub repositories, and a derived context inferred from graded attempts.
  2. Bounded context growth. Compress interaction history into a fixed-length summary regenerated at intervals, so that prompt size is independent of the number of attempts completed.
  3. Calibrated assessment. Implement a ten-point rubric that separates considered responses from superficial ones, and produces feedback naming specific behaviour rather than generic advice.
  4. Adaptive difficulty. Scale scenario difficulty from a rolling average of recent scores and its short-term trend, seeded initially from self-rated confidence.
  5. Graceful degradation. Provide a model fallback chain and a deterministic offline scenario bank so that rate limiting does not render the application unusable.
  6. Habit-oriented gamification. Implement experience points, levels, daily streaks, per-track skill scores and a composite Professional Readiness Score.

1.4 Scope and Limitations

1.4.1 In Scope

The delivered system covers three training tracks (Workplace Communication, Critical Thinking and AI Fluency); email-and-password account creation with server-side session management; an eight-field onboarding profile; optional GitHub linkage; AI-generated scenarios and AI-graded responses; the complete gamification engine; a dashboard, profile page and full attempt history with detail replay; and a responsive interface usable on both desktop and mobile browsers.

1.4.2 Out of Scope

The following were deliberately excluded to keep the work defensible within a mini-project timeframe, and are discussed as future enhancements in Chapter 7: peer leaderboards and social comparison; achievement badges; a graphical skill-tree; a fully developed AI hallucination-detection curriculum beyond the AI Fluency track's scenarios; email verification and password recovery; and native mobile applications.

1.4.3 Acknowledged Limitations

Three limitations are stated at the outset rather than concealed, and are analysed quantitatively in Section 6.7. First, assessment is performed by a single model instance with no second grader, so inter-rater reliability has not been established. Second, the offline scenario bank contains eighteen hand-written scenarios; during a prolonged outage a frequent user will encounter repetition. Third, the evaluation reported in Chapter 6 uses a small number of synthetic trainee profiles rather than a longitudinal study with real students, and therefore demonstrates that the mechanisms behave as designed rather than that learning outcomes improve.

Chapter 2
Literature Survey

2.1 Existing Soft-Skill Training Systems

Commercial and institutional soft-skill training divides into three families. Content libraries such as recorded MOOC modules deliver expert instruction at scale but assess through multiple-choice questions, which measure recall of communication theory rather than the ability to communicate. Assessment platforms used in campus placement preparation administer aptitude and situational-judgement tests; these are closer to practice, but the situations are drawn from a fixed bank, are identical for every candidate, and permit the candidate to select a pre-written option rather than compose a response. Human-led workshops — mock interviews and group discussions — provide genuine practice with individualised feedback, and are the most effective of the three, but their cost scales linearly with the number of students and they occur a handful of times per academic year rather than daily.

The recurring weakness across the first two families is the absence of production. A trainee who never writes the difficult message never practises writing the difficult message. The weakness of the third is frequency: behavioural change requires repetition, and a twice-a-semester workshop provides none.

2.2 Large Language Models as Assessors of Free-Text Responses

Automated essay scoring has an established literature, historically based on hand-engineered features such as length, lexical diversity and syntactic complexity. Such features are proxies and are trivially gamed: a verbose, well-punctuated but substantively empty answer scores highly. This limitation is directly relevant here, and is the reason the offline heuristic described in Section 5.7 is explicitly capped and labelled rather than presented as equivalent to model grading.

Instruction-tuned language models changed the position because they can be given a rubric in natural language and asked to apply it, with justification. Reported concerns are that models tend toward leniency, exhibit sensitivity to response length independent of quality, and can reward fluency over correctness. The mitigations adopted in this work follow from those concerns: the rubric enumerates explicit score bands with behavioural descriptors; the prompt states that inflated scores make the training worthless; a hard ceiling is imposed on very short responses; and the grader is instructed to quote or paraphrase what the trainee actually wrote, which discourages generic praise. Section 6.3 reports the separation achieved in practice.

2.3 Context Management in Long-Running LLM Applications

An application that personalises from accumulated history faces a well-known scaling problem. Three strategies appear in practice. Full-history injection places all prior interactions in the prompt; it is simple and preserves detail, but cost and latency grow without bound and quality degrades as the relevant signal is diluted. Retrieval-augmented generation embeds history in a vector store and retrieves the most similar items; cost is bounded, but it requires embedding infrastructure and retrieves items similar to the query rather than items describing the learner. Recursive summarisation maintains a compact summary that is periodically rewritten from recent interactions plus the previous summary; cost is constant and the summary is explicitly about the learner, at the price of losing detail not carried forward.

For this application the third strategy is the correct one, because the object of interest is not any individual past attempt but the behavioural pattern across attempts — precisely what a summary encodes and what retrieval does not. The design is described in Section 5.4.

2.4 Gamification and Habit Formation

The gamification literature distinguishes mechanics that support intrinsic motivation from those that substitute for it. Progress feedback, visible competence growth and streak mechanics are associated with sustained engagement; leaderboards and inter-personal comparison are associated with short-term engagement but can reduce intrinsic motivation among lower-ranked participants and encourage metric-gaming.

This influenced two decisions. Leaderboards were excluded from scope despite being straightforward to implement, because a public ranking of communication ability among classmates would plausibly deter the students who most need the practice. Second, the streak indicator was designed as a passive visual state — the flame dims in the evening if the day's quest is incomplete — rather than as a notification, since intrusive reminders are a common cause of disengagement.

System Requirements and Analysis

3.1 Functional Requirements

The system shall satisfy the following functional requirements.

FR-1 Account Management

The system shall permit registration with an email address and password of at least eight characters; shall store passwords only in salted, key-derived form; shall establish an authenticated session on successful login; and shall permit explicit termination of that session. Authentication failures shall not disclose whether an email address is registered.

FR-2 Profile Capture

The system shall collect an eight-field profile covering academic year, branch, target role, prior team experience, preferred work setting, self-identified difficulties (maximum three) and self-rated confidence for each track. Each field shall be presented individually. The profile shall be editable after onboarding, and edits shall take effect on subsequently generated scenarios.

FR-3 Portfolio Linkage

The system shall optionally accept a public GitHub username, retrieve the user's non-forked and non-archived repositories, derive the technologies and problem domains represented, and present the derived summary for inspection. The linkage shall be removable, and its absence shall not prevent any other function.

FR-4 Scenario Generation

Given a selected track, the system shall generate a workplace scenario of two to four sentences conditioned on the stated profile, the derived portfolio and the derived learner context, at a difficulty determined by the trainee's rolling score in that track. Consecutively generated scenarios for the same trainee and track shall not be near-duplicates.

FR-5 Response Assessment

The system shall accept a free-text response of at least eight words, return an integer score in the range 1–10, and return three feedback components: what worked, what was missing, and one specific improvement. Where a weakness recorded in the derived context recurs, the feedback shall identify it as recurring.

FR-6 Progression Tracking

The system shall award experience points as a function of score and streak, maintain level bands, maintain a daily streak that increments once per calendar day and resets after a missed day, maintain a rolling per-track skill score, and compute a composite Professional Readiness Score.

FR-7 History and Review

The system shall retain every attempt and permit the trainee to review any past attempt in full, including the original scenario, their response and the feedback received, with filtering by track.

FR-8 Degraded Operation

On failure of the primary inference model, the system shall attempt an alternative model. On failure of all models, it shall serve a scenario from a local bank and assess using a deterministic rubric, and shall label such output as offline-generated in the interface.

Chapter 4
System Design

4.1 Architectural Overview

The system follows a three-tier architecture organised as a monorepo. The presentation tier is a single-page application; the application tier is a stateless REST service apart from server-persisted sessions; the data tier is an embedded SQLite database. External inference and repository-metadata services are treated as unreliable dependencies, accessed only through adapter modules that encapsulate retry, fallback and degradation policy.

A deliberate deployment decision is that the API binds only the loopback interface. During development the frontend dev server is exposed on the local network so the application can be tested on a phone, but requests reach the API only through a server-side proxy. Consequently the database file and the inference credential are never reachable from the network.

The REST interface exposed by the application tier is summarised in Table 4.1. Two guard middlewares are applied: requireAuth rejects unauthenticated requests, and requireOnboarded additionally rejects requests from accounts without a completed profile. The latter is applied to the entire quest router, on the reasoning that scenario quality is the substance of the system and an unpersonalised scenario would misrepresent it.

4.3 Database Design

Persistence uses five relations. SQLite operates in write-ahead logging mode, which permits concurrent readers alongside a writer and improves throughput for the read-dominant access pattern of the dashboard. Foreign-key enforcement is enabled explicitly, as SQLite disables it by default. 4.4 Data-Flow Design

The separation of process 5.0 from the request path is a deliberate performance decision. Context regeneration requires an additional model call of comparable latency to grading itself. Executing it synchronously would approximately double the perceived wait after every third submission. As the summary is used only to condition subsequent generations, a summary that is one cycle stale is harmless, whereas a doubled wait is directly felt. The refresh is therefore dispatched after the HTTP response is written, and its failure is logged without affecting the user-visible outcome.

4.5 Quest Lifecycle — Sequence Design

Step 9 executes inside a single SQLite transaction covering both the insertion of the attempt and the mutation of the user's experience points, streak and longest-streak record. Were these separate statements, an interruption between them could award experience without recording the attempt that justified it, permanently corrupting the relationship between the attempt log and the progression state.

4.6 Personalisation Pipeline

Figure 4.6 shows the composition of the three personalisation signals. The essential property is that each signal enters the prompt in a bounded form. The stated profile is a fixed number of enumerated fields; the portfolio contributes at most six technologies and three domains; the derived context is a summary constrained to sixty words with at most three recurring-gap phrases. No component grows with usage.

Chapter 5
Implementation

5.1 Authentication and Session Management

Passwords are protected using scrypt from the Node.js standard crypto module, with parameters N = 16384, r = 8, p = 1 and a 64-byte derived key, each password receiving an independent 16-byte random salt. Scrypt was selected over bcrypt for two reasons: it is memory-hard, which raises the cost of parallel hardware attack more effectively than bcrypt's purely CPU-bound work factor, and it is available in the platform standard library, which avoids introducing a second native compilation step into a project that already required one for the database driver. Comparison of the derived key against the stored value uses a constant-time routine, preventing timing-based recovery. 

const SCRYPT = { N: 16384, r: 8, p: 1, keylen: 64 }

export async function hashPassword(password) {
  const salt = randomBytes(16)
  const key  = await scryptAsync(password, salt, SCRYPT.keylen, SCRYPT)
  return `scrypt$${SCRYPT.N}$${SCRYPT.r}$${SCRYPT.p}$` +
         `${salt.toString('base64')}$${key.toString('base64')}`
}

Storing the parameters alongside the digest means that the work factor can be raised in future without invalidating existing credentials, since verification reads the parameters from the stored record rather than assuming current constants.

Sessions use 32 bytes of cryptographically secure random data, transmitted in an HTTP-only cookie with SameSite=Lax and a thirty-day expiry. Only the SHA-256 digest of the token is persisted. This means that a disclosure of the database does not yield usable session tokens — an attacker obtains digests from which the originals cannot be recovered. Expired records are purged at process start. Login returns an identical error message and performs comparable work whether or not the supplied email exists, so the endpoint cannot be used to enumerate registered addresses.

5.2 Stated Profile Module

The eight profile fields are defined once, on the server, in profile.js. The client retrieves these definitions at runtime rather than duplicating them. This eliminates a common defect class in which validation rules and interface options diverge after a change. Each option carries two strings: a label shown to the trainee, and a prompt phrase used when constructing the model input. Separating them allows the interface to read naturally while the model receives phrasing suited to generation.

Age is not collected. Academic year conveys everything age would convey for the purpose of calibrating scenario difficulty, and personal data that does not alter system output is not retained.

5.3 GitHub Portfolio Distiller

The distiller retrieves the account profile and repository listing, filters to owned repositories that are neither forks nor archived, orders by star count and recency, and retains at most ten. For the five strongest it additionally retrieves the README, strips fenced code blocks, badge images and HTML markup, and truncates to 1500 characters. The resulting corpus is passed once to the model, which returns a short brief, a technology list of at most six entries, a domain list of at most three, and a coarse level estimate.

Two filtering decisions warrant justification. Forks are excluded because a forked tutorial repository is not evidence of authorship; including forks would characterise many students by material they did not write. READMEs are treated as enrichment rather than as the primary signal, with automatically generated scaffolding readmes detected and discarded. This is contrary to the intuitive approach of reading documentation first, and follows from an observation about the target population: a large proportion of student repositories contain either a single-line README or an unmodified framework template. Repository language, description, topics and recency are almost always present, and therefore lead. A README-first design would perform well on a well-documented account and return nothing usable on a typical one.

Failure conditions are distinguished rather than collapsed: a malformed username is rejected before any network call; a non-existent account, an account with no owned public repositories, and API rate limiting each produce a distinct message. Should the distillation model call fail, the linkage is not persisted — an unlinked account is preferable to a stored portfolio that was never actually derived.

5.4 Derived Learner Context

The derived context is the mechanism by which the system improves with use. Rather than accumulating attempts, the model is periodically asked to rewrite a description of the trainee from a recent window plus the previous description. Refresh occurs when three attempts have accumulated since the last update; the window is the six most recent attempts. The output is constrained to a summary of at most sixty words, at most three recurring-gap phrases of at most eight words each, and a single clause identifying what the next scenario should force the trainee to confront.

The summarisation prompt requires behavioural specificity, instructing that “gives timelines but never explains the cause of a delay” is useful whereas “needs improvement” is not, and that only patterns occurring more than once may be reported as recurring. The resulting summary is injected into both scenario generation and grading. In grading it enables the model to identify repetition explicitly; the prompt states that where a previously flagged weakness recurs, saying so plainly is more useful than treating it as novel, and equally that a corrected weakness should be acknowledged. Section 6.5 reports the observed behaviour.

5.5 Prompt Engineering and Anti-Recitation

Personalisation introduces a failure mode that does not arise in unpersonalised generation. When a model is supplied with a description of the reader, it tends to restate that description in its output. Early scenarios began “As a final-year Computer Science student aiming for a software role, you…”, which is both unnatural and pedagogically useless: the trainee is placed outside the situation and asked to observe themselves rather than to act.

The mitigation is an explicit statement of the role the background plays, positioned after the generation rules where the model's attention is nearest to output: 

CRITICAL — how to use the background above:
It decides the SETTING, who else is in the room, how senior they are, and what
is at stake. It is NOT part of the scenario. Never state or hint at the
trainee's year of study, branch, career goal, confidence, or past performance.
Do not open with "As a final-year student" or anything like it. Write the
situation as it would actually be experienced, from inside it.

A second constraint governs technology. The model may use one technology from the derived stack to make the situation concrete, must vary which one it selects across generations, and must invent a fresh product or feature each time. It is forbidden from naming the trainee's repositories or describing their personal projects back to them. The final clause is a proportionality instruction — the track concerns a human problem, and technology is texture rather than substance.

De-duplication operates on two lists. Completed attempts for the track are read from the database, and scenarios that were generated but never answered are held in a bounded in-memory structure of six entries per trainee and track. The second list exists because a trainee who repeatedly requests a different scenario generates nothing persistent; without it, the de-duplication input is empty and near-identical scenarios are returned. The structure is intentionally not persisted, as it is a generation hint rather than data of record, and the map itself is capped to prevent unbounded growth in a long-running process.

5.7 Resilience: Fallback Chain and Offline Bank

The free inference tier is served from a shared upstream pool and returns HTTP 429 under load; this was observed repeatedly during development and is a normal operating condition rather than an exceptional one. Three mechanisms are layered in response.

First, transient status codes (408, 429 and 5xx) trigger up to three retries with increasing delay. Second, exhausting retries advances to the next model in a configured chain. Third, if all models fail, a local bank of eighteen hand-written scenarios — three tracks by three difficulty bands, two scenarios each — supplies content, and a deterministic rubric supplies a score.

The deterministic rubric is bounded above at seven, and its response text states plainly that the model was unreachable and the score should be treated as approximate. This honesty is deliberate. The rubric rewards length, the presence of a concrete detail such as a number or date, evidence of a verification step, and use of first-person commitment language. These are proxies, and, as noted in Section 2.2, proxies of exactly the kind that a verbose but empty response can exploit. Presenting such a score as equivalent to model assessment would misrepresent it, so the interface labels every offline result explicitly.

Honest scope of the resilience claim. The system degrades gracefully; it does not achieve full independence from the inference provider. With eighteen stored scenarios, a trainee who continues through an extended outage will encounter repetition, and the offline score is a heuristic rather than an assessment. The claim supported by the implementation is that a rate-limit event does not interrupt a session — not that the system is equivalent when offline.

6.3 Grader Calibration

Calibration was assessed by submitting responses of deliberately differing quality to comparable scenarios. A considered response — one that acknowledged the constraint, proposed a specific alternative with a named date, and offered the recipient a choice — received 9/10. A dismissive single sentence (“I would just fix it and tell them it is done.”) received 1/10 against a comparable scenario. A superficially courteous but substantively empty response, asserting the importance of communication without committing to any action, received 2–3/10 and was described as “describing your intent to communicate rather than providing the actual technical justification”.

The eight-point spread between the strongest and weakest response is the material result. A grader that clustered all responses between 6 and 8 would render the skill score meaningless and the adaptive difficulty inoperative, since both derive from score variance.

6.5 Derived Context Validation

The derived context was validated by planting a deliberate behavioural pattern. Three consecutive attempts across two tracks were answered with variations of the same evasive response, asserting the value of communication without committing to any concrete action. After the third attempt the refresh cycle produced:

Summary: “The trainee demonstrates a positive attitude toward teamwork and communication. However, they consistently provide vague, non-committal responses that avoid addressing specific technical conflicts or underlying risks. They tend to describe their intent to communicate rather than providing concrete actions, technical justifications, or specific dialogue to resolve issues.”

Recurring gaps: [“avoids addressing technical conflicts”, “provides vague non-committal responses”]

Push next: “provide specific technical justifications and concrete action steps”

The summary correctly identifies the planted pattern and distinguishes it from a superficial reading — it notes the positive intent while naming the behavioural deficiency precisely. The subsequent test submitted the same evasive response a fourth time. The grader responded:

“This is the same gap as last time; you are describing your intent to communicate rather than providing the actual technical justification or concrete next steps required to resolve the conflict.”

This completes the intended loop. The system observed a pattern across attempts, compressed it into a bounded representation, carried it forward, and used it to produce feedback that a stateless grader could not have produced. It is the behaviour that distinguishes the system from one which merely adjusts a difficulty parameter.

6.6 Observed Failure Mode and Remediation

Testing of the GitHub feature revealed a defect that had not been anticipated. With a portfolio linked, two independently generated scenarios for the same track were returned:

(a) “…bypass the sensor calibration tests to meet the Friday deployment deadline for the waste management prototype…”

(b) “…bypass the TensorFlow Lite optimisation phase to meet the Friday deployment deadline for the waste management sensor…”

The two are near-identical in subject, deadline and structure. The cause was traced to the free-text portfolio brief, which named a specific project — an edge-AI waste management system — and which was being supplied to the generation prompt. Given a single concrete subject, the model anchored on it and produced variations of one situation rather than exploring the space.

The remediation separates the brief by purpose. It is retained for display, where naming a real project is precisely what makes the derived portfolio legible and verifiable to the trainee. It is removed from prompt input, which now receives only the bounded technology and domain lists. These provide equivalent technical concreteness while offering no single subject on which to fixate. An instruction to vary the technology selected and invent a fresh product each time was added in the same change. Three subsequent generations produced distinct situations — a TensorFlow Lite unit-test dispute, an Arduino IoT gateway threshold argument, and a TypeScript schema shortcut on an Astro dashboard — with different colleagues and different seniority in each.

The episode is reported rather than omitted because it illustrates a general property of prompt-conditioned personalisation: the value of a signal to a human reader and its suitability as model input are independent questions. The most informative summary for a person was the most harmful input for the generator.

6.7 Threats to Validity

The results above establish that the implemented mechanisms behave as designed. They do not establish that the system improves soft-skill competence, and the following constraints on interpretation are stated explicitly.

6.7.1 Construct Validity

Assessment is performed by a single model instance with no independent second grader. Agreement with expert human raters has not been measured, so it cannot be asserted that a score of 7 corresponds to what an experienced engineering manager would assign. The demonstrated property is discrimination — that clearly different response qualities receive clearly different scores — which is weaker than validity but is the necessary precondition for it.

6.7.2 Internal Validity

Generation is stochastic. The scenario comparisons in Table 6.2 are single samples per condition, and some differences between them may reflect sampling variation rather than the profile substitution. The differences observed are large and systematic — a hardware defect against a code review — which makes chance an unlikely explanation, but a controlled study would require repeated sampling per condition and blind classification of outputs.

6.7.3 External Validity

Profiles used in testing were synthetic and constructed by the authors. Real trainees may report profiles inconsistently, may not possess a GitHub account with usable content, or may produce responses in registers not represented in testing. No longitudinal deployment was conducted, so retention and learning outcomes are unmeasured.

6.7.4 Operational Constraints

Three implementation constraints bound the deployment claim. Streak computation uses the server's local calendar date, which is correct for the intended single-host deployment but would require per-user timezone handling in a hosted multi-region deployment. The unauthenticated GitHub API permits sixty requests per hour and a single profile synchronisation consumes approximately seven, which is adequate for individual use but not for concurrent classroom use without a configured access token. Finally, the offline bank's eighteen scenarios bound the duration of an outage that can be absorbed without repetition.

Chapter 7
Conclusion and Future Enhancements

7.1 Conclusion

This work set out to determine whether soft-skill training could be made genuinely individual rather than merely automated, and whether that individualisation could be sustained without the inference cost growing with use. Both questions are answered affirmatively by the delivered system.

Personalisation was achieved by combining three independent signals — a stated profile, a distilled public code portfolio, and a derived behavioural context — each represented in a form whose size is fixed by construction. Substituting these inputs produces materially different scenarios: an electronics student targeting core engineering receives a printed-circuit-board defect raised in a sprint review, while a computer science student targeting a startup receives a pull-request disagreement with a colleague at the adjacent desk. The grader discriminates across an eight-point range between considered and evasive responses, which is the precondition for the skill score and adaptive difficulty to carry information.

The most substantive contribution is the derived context mechanism. By rewriting a bounded summary every three attempts rather than accumulating history, the system carries forward what it has learned about a trainee at constant cost. Its effect is directly observable: after a deliberately planted pattern of evasive responses, the system identified the behaviour, recorded it, and produced feedback that opened “this is the same gap as last time”. A stateless implementation cannot produce that sentence, and it is the sentence a human mentor would say.

Equally instructive was a defect encountered during evaluation. Supplying the model with a free-text summary naming a specific project caused it to anchor, generating variations of one situation. The resolution — retaining the summary for human display while restricting model input to bounded category lists — reflects a principle worth carrying forward: the representation best suited to informing a person is not necessarily the representation best suited to conditioning a generator, and conflating the two degrades output in ways that are not obvious until measured.

The system's limitations are known and documented. Assessment rests on a single unvalidated grader; evaluation used synthetic profiles rather than a student cohort; and the offline mode degrades gracefully without being equivalent. These bound what may be claimed, and are stated so that the claims made are defensible.

7.2 Future Enhancements

  1. Grader validation against human raters. The highest-value next step. Collecting expert ratings for a corpus of responses and measuring agreement would convert the discrimination result of Section 6.3 into a validity claim, and would identify systematic bias in specific score bands.
  2. Second-opinion grading. Sampling two independent gradings and reconciling divergence beyond a threshold would reduce variance, at roughly double the inference cost per submission.
  3. Spoken-response track. Group discussions and interviews are spoken. Adding speech capture with transcription would extend the system to the modality in which placement assessment actually occurs.
  4. Expanded offline bank with procedural variation. Parameterising the stored scenarios over names, technologies and deadlines would raise the effective offline capacity substantially without proportionate authoring effort.
  5. Achievement badges and a skill-tree visualisation. Deferred from the present scope; both are compatible with the existing progression model. Leaderboards remain deliberately excluded for the reason given in Section 2.4.
  6. Instructor view. An aggregate, anonymised view of common weaknesses across a class would let a department identify which competencies to address in teaching, converting individual practice data into curricular signal.
  7. Account recovery and native mobile clients. Email verification and password reset are prerequisites for deployment beyond a controlled setting; the interface is already responsive, so a wrapped or native mobile client is an incremental rather than architectural change.
