Abstract — Recruiters consistently report that engineering graduates fail on communication, reasoning under ambiguity and uncritical use of AI tools rather than on technical knowledge. These are behavioural skills, acquired by repeated attempts followed by specific feedback, yet they are taught through lecture videos and multiple-choice tests in which the student never actually composes a difficult message. This work presents Knack, a web application that reframes soft-skill practice as a five-minute daily exercise. A trainee selects one of three tracks, receives a workplace scenario generated by a large language model, writes the response they would genuinely send, and is graded 1–10 with feedback naming what worked, what was missing and one concrete improvement. Scenarios are conditioned on three independent signals — an eight-field stated profile, an optional distillation of the trainee's public GitHub repositories, and a derived learner context the model rewrites every three attempts. Because only the rewritten summary is injected and never the raw history, prompt size stays constant however long the trainee trains. Measured results show an eight-point grader separation between considered and evasive responses, correct detection of a deliberately planted recurring weakness, and materially different scenarios under substituted profiles.

Keywords: Large Language Models, Prompt Engineering, Personalised Learning, Context Compression, Gamification, Adaptive Difficulty, Full-Stack Web Development.

1. Introduction

A graduate who can implement a balanced binary search tree may still be unable to tell a team lead that an estimate has slipped, to notice that a stated requirement does not match the real need, or to catch that a generated code snippet calls a library function which does not exist. Existing training is declarative — a student can score full marks on a communication assessment without ever having written a difficult message.

Instruction-tuned language models now make a different approach viable: they can generate specific workplace situations and assess free-text responses against a stated rubric. The remaining difficulty is that a generic AI tutor is only marginally better than a generic video. If every trainee receives the same scenarios, the system is a content library with added latency. Value appears only when the situation resembles the one the trainee will actually walk into — which requires the system to know who they are, what they build, and where they have previously failed.

That requirement creates the central engineering constraint. The obvious way to personalise from history is to place past attempts into the prompt, but this makes cost grow linearly with usage and measurably degrades output on a small model. A system that becomes slower, more expensive and worse the more it is used is not a training system.

2. Objectives

  1. To personalise scenario generation using three independent signals — a stated profile, a distilled public code portfolio, and a context derived from graded attempts.
  2. To hold prompt size constant irrespective of accumulated history, by compressing that history into a bounded summary rewritten at intervals.
  3. To implement a calibrated 1–10 rubric that separates considered from superficial responses and returns behaviourally specific feedback.
  4. To scale scenario difficulty from a rolling average of recent scores and its short-term trend.
  5. To degrade gracefully through a model fallback chain and a local scenario bank when the free inference tier is rate-limited.
  6. To implement XP, levels, daily streaks, per-track skill scores and a composite Professional Readiness Score.

3. System Architecture

The system is a three-tier monorepo. A React single-page application forms the presentation tier; an Express service forms the application tier; an embedded SQLite database forms the data tier. External inference and repository-metadata services are treated as unreliable dependencies and reached only through adapter modules that own all retry, fallback and degradation policy. The API binds the loopback interface only, so the database file and the inference credential are never reachable from the network even when the development server is exposed for mobile testing.

4. Methodology

A trainee registers, completes an eight-field profile presented one question per screen, and optionally links a public GitHub account. On selecting a track, the server loads the stated profile, the distilled portfolio and the derived context, determines difficulty from the rolling skill score, composes a prompt and requests a scenario. The trainee writes a response; the server grades it against a rubric, persists the attempt, awards XP and updates the streak inside a single transaction, and returns the result. After the response is sent, a background job rewrites the learner summary if three attempts have accumulated since the last refresh.

6. Multi-Source Personalisation

Three signals condition every generated scenario, and each is bounded by construction. The stated profile contributes eight enumerated fields — year, branch, target role, experience, work setting, self-identified difficulties and per-track confidence. The GitHub portfolio contributes at most six technologies and three problem domains. The derived context contributes a summary of at most sixty words and at most three recurring-gap phrases.

7. Working Principle

7.1 Derived Learner Context

Rather than accumulating attempts, the model is periodically asked to rewrite a description of the trainee from a six-attempt window plus the previous description. The summarisation prompt demands behavioural specificity — “gives timelines but never explains the cause of a delay” is useful, “needs improvement” is not — and permits only patterns occurring more than once to be reported as recurring. The summary feeds both generation and grading, so the grader can name a repeated mistake explicitly instead of treating every attempt as the first.

7.2 Prompt Engineering and Anti-Recitation

Personalisation introduces a failure mode absent from generic generation: given a description of the reader, the model restates it. Early scenarios opened “As a final-year Computer Science student aiming for a software role, you…”, which places the trainee outside the situation and asks them to observe themselves rather than act. The prompt therefore states explicitly that the background selects the setting, the other people present and the stakes, and must never appear in the scenario text. A second rule permits one technology from the trainee's stack to be used for concreteness, requires it to vary between generations, and forbids naming their actual repositories.

7.3 Resilience

The free inference tier is served from a shared pool and returns HTTP 429 under load — a normal operating condition rather than an exception. Transient failures trigger up to three retries with increasing delay; exhausting them advances to the fallback model; failure of all models falls back to eighteen local scenarios and a deterministic rubric capped at 7. Offline output is tagged and labelled in the interface, never presented as model output.

The eight-point grader spread is the material result: a grader clustering every response between 6 and 8 would make the skill score meaningless and adaptive difficulty inoperative, since both derive from score variance.

8.1 Observed Failure Mode

Testing of the GitHub feature revealed a defect worth reporting. With a portfolio linked, two independently generated scenarios returned near-identical situations — both concerning the same project subject and the same “Friday deployment deadline”. The cause was the free-text portfolio brief, which named a specific project and was being supplied to the generation prompt; given one concrete subject, the model anchored on it. The remediation separates the brief by purpose: it is retained for display, where naming a real project makes the inference verifiable to the trainee, and removed from prompt input, which now receives only the bounded technology and domain lists. Three subsequent generations produced distinct situations with different colleagues and different technologies.

The representation best suited to informing a person is not necessarily the representation best suited to conditioning a generator — and conflating the two degrades output in ways that are not obvious until measured.

9. Advantages and Limitations

Advantages — free-text production with individualised feedback rather than multiple choice; personalisation from three independent signals including demonstrated weakness; inference cost bounded irrespective of usage; graceful degradation under rate limiting; and a daily practice cadence rather than periodic workshops.

Limitations — assessment rests on a single model instance with no second grader, so agreement with expert human raters is unmeasured and only discrimination has been demonstrated, not validity. Evaluation used synthetic trainee profiles rather than a student cohort, so learning outcomes are unproven. The offline bank holds eighteen scenarios, so a prolonged outage will produce repetition. Streak computation uses the server's local calendar date, correct for single-host deployment but not for a multi-region one.

10. Conclusion and Future Scope

Knack demonstrates that soft-skill training can be made genuinely individual rather than merely automated, and that the individualisation can be sustained at constant inference cost. Its most substantive contribution is the derived context mechanism: by rewriting a bounded summary every three attempts instead of accumulating history, the system carries forward what it has learned about a trainee without cost growth, and its effect is directly observable in feedback that opens “this is the same gap as last time” — a sentence a stateless implementation cannot produce, and the sentence a human mentor would say.

Future scope — validation of the grader against expert human raters, which would convert the discrimination result into a validity claim; two-grader reconciliation to reduce variance; a spoken-response track, since placement assessment is spoken; procedural variation of the offline bank to raise effective capacity; an anonymised instructor view turning individual practice data into curricular signal; and account recovery plus a native mobile client.
